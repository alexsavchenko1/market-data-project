Мне было интересно не только получить данные, но и разобраться, как организовать параллельную работу с независимыми HTTP-запросами, обработать сбои внешнего сервиса и сделать результат каждого запуска проверяемым.

Тематика проекта была выбрана не случайно. Во-первых, многопоточность уже встречалась мне в одной из рабочих задач, поэтому я хотел лучше понять её на практике. ## Что делает приложение

На вход приложение получает CSV-файл со списком тикеров, периодами и интервалами загрузки.

Пример входного файла:

```csv
symbol,date_from,date_to,interval
AAPL,2025-01-01,2025-01-10,1d
MSFT,2025-01-01,2025-01-10,1d
NVDA,2025-01-01,2025-01-10,1d
```

После запуска приложение:

1. проверяет корректность входных данных;
2. получает исторические цены через HTTP API Yahoo Finance;
3. параллельно обрабатывает запросы по разным тикерам;
4. преобразует ответы внешнего сервиса во внутренние модели;
5. сохраняет историю каждого тикера в отдельный CSV-файл;
6. нормализует цены к начальному значению 100;
7. строит сравнительный график;
8. формирует итоговый отчёт и журнал событий.

Общая схема работы выглядит следующим образом:

```text
CSV с запросами ->
параллельные HTTP-запросы ->
ограниченная очередь результатов ->
сохранение отдельных CSV-файлов ->
нормализация данных и построение графика
```

## Параллельная обработка

Запросы по разным тикерам не зависят друг от друга. При последовательном выполнении приложение большую часть времени ожидает ответа внешнего сервиса, поэтому для загрузки я использовал пул рабочих потоков.

Количество потоков задаётся через настройки приложения. Полученные данные передаются через ограниченную очередь в отдельный поток записи.

Ограничение размера очереди нужно для того, чтобы результаты не накапливались в памяти без контроля, если загрузка выполняется быстрее, чем сохранение файлов. Таким образом, получение данных и их запись разделены, но количество ожидающих сохранения результатов остаётся ограниченным.

В проекте также оставлен последовательный вариант загрузки. Он используется как базовая точка сравнения и позволяет проверить реальный эффект от параллельного выполнения.

## Работа со сбоями

Внешний сервис может отвечать медленно, временно быть недоступным или ограничивать частоту запросов. Поэтому приложение повторяет запросы при:

- сетевых ошибках;
- тайм-аутах;
- HTTP 408;
- HTTP 429;
- HTTP 5xx.

Между попытками используется увеличивающаяся задержка. Такой подход был мне знаком по рабочим задачам, поэтому я решил воспроизвести его и в учебном проекте.

Количество попыток и параметры задержки можно менять через переменные окружения.

Ошибка одного тикера не останавливает весь запуск. Успешно полученные данные сохраняются, а информация о неудачном запросе добавляется в итоговый отчёт. Это позволяет получить частичный результат даже в ситуации, когда внешний поставщик не смог обработать один из запросов.

## Наблюдаемость

После каждого запуска приложение формирует два файла:

```text
data/reports/latest.json
data/logs/latest.jsonl
```

В итоговом JSON-отчёте сохраняются:

- идентификатор запуска;
- время начала и завершения;
- количество входных запросов;
- число загруженных и сохранённых историй;
- количество ошибок загрузки и записи;
- число повторных попыток;
- продолжительность загрузки;
- информация о созданном графике.

Журнал событий содержит более подробную последовательность выполнения: начало запуска, успешные загрузки, повторные запросы, ошибки и завершение обработки.

Я добавил отчёт и журнал, чтобы результат работы приложения можно было проверить не только по сообщениям в терминале. Кроме того, они позволяют сопоставить итоговые показатели с конкретными событиями одного запуска.

## Тестовый сервис на Go

Для проверки временных ошибок и задержек мне был нужен управляемый внешний сервис. При работе с реальным API невозможно заранее определить, когда именно он вернёт `429` или `503`, поэтому такие проверки сложно воспроизводить.

Я написал небольшой HTTP-симулятор на Go. Для меня это стало первой практической работой с этим языком. Симулятор намеренно оставлен простым и используется только как вспомогательный тестовый инструмент.

Он поддерживает несколько сценариев:

| Тикер | Поведение |
|---|---|
| обычный тикер | успешный ответ |
| `SLOW` | ответ с искусственной задержкой |
| `FLAKY` | две ошибки `503`, затем успешный ответ |
| `RATE` | две ошибки `429`, затем успешный ответ |
| `FAIL` | постоянная ошибка `503` |

В проверочном сценарии Python-приложение получило пять запросов. Четыре из них были успешно обработаны, а запрос `FAIL` завершился ошибкой после исчерпания всех попыток.

При этом приложение сохранило остальные результаты, выполнило шесть повторных запросов и корректно завершило работу. Медленный ответ также не заблокировал выполнение остальных запросов.

Этот сценарий подтвердил, что временные ошибки обрабатываются повторно, постоянный сбой одного запроса не останавливает всю обработку, а успешно полученные данные не теряются.

## Результаты параллельной обработки

Для сравнения последовательного и параллельного вариантов я подготовил десять независимых запросов. Тестовый сервис задерживал каждый ответ на одну секунду.

| Количество рабочих потоков | Время загрузки |
|---:|---:|
| 1 | 10,037 с |
| 5 | 2,013 с |

В этом сценарии переход с одного рабочего потока на пять сократил время загрузки примерно в **4,99 раза**.

Этот результат не является универсальной оценкой производительности приложения. Эксперимент проводился на независимых сетевых запросах с одинаковой искусственной задержкой. Он показывает именно то, что при ожидании внешнего сервиса потоки позволяют не выполнять каждый запрос строго последовательно.

## Автоматический запуск

Я не стал разворачивать проект как постоянно работающий веб-сервис, потому что он решает пакетную задачу: получает список запросов, обрабатывает их и сохраняет результат.

Для автоматического запуска я настроил GitHub Actions. После отправки изменений в репозиторий GitHub:

1. создаёт чистое окружение;
2. устанавливает Python и Go;
3. устанавливает зависимости проекта;
4. запускает тесты и статические проверки;
5. проверяет Go-симулятор;
6. поднимает локальный тестовый сервис;
7. запускает Python-приложение;
8. сохраняет CSV-файлы, график, отчёт и журнал событий как артефакты workflow.

Так полный сценарий проекта можно воспроизвести независимо от настроек моего компьютера. Успешный запуск GitHub Actions также подтверждает, что проект собирается и работает в чистом окружении.

## Ограничения

Проект не является торговой системой и не используется для принятия инвестиционных решений.

Данные сохраняются локально, а приложение рассчитано на пакетную обработку сравнительно небольшого списка тикеров.

В качестве основного источника используется неофициальный HTTP API Yahoo Finance, поэтому его формат или доступность могут измениться.

Go-сервис является только тестовым симулятором внешнего поставщика и не рассматривается как отдельный продуктовый компонент.
