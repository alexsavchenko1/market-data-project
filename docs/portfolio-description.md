# Сервис параллельной загрузки и сравнения рыночных данных

**Репозиторий:** [github.com/alexsavchenko1/market-data-project](https://github.com/alexsavchenko1/market-data-project)

## О проекте

Я разработал сервис пакетной обработки рыночных данных, который получает историю цен через внешний HTTP API, параллельно обрабатывает запросы по нескольким тикерам, сохраняет результаты в отдельных CSV-файлах и строит сравнительный график.

Основной целью проекта было не само получение биржевых данных, а практическая работа с параллельными сетевыми запросами, ограниченной очередью, частичными отказами и наблюдаемостью выполнения. Мне хотелось пройти весь путь от простого сценария загрузки данных до приложения, поведение которого можно проверить в штатных условиях, при задержках внешнего сервиса и при различных типах ошибок.

Базовая идея проекта была предложена на курсе «Многопоточность в Python: от новичка до эксперта». Изначальная задача заключалась в получении исторических цен, сохранении данных и построении графика. Дальнейшую структуру приложения, обработку ошибок, повторные запросы, отчётность, тестовый сервис, измерение производительности и автоматический запуск я реализовал самостоятельно.

Тематика проекта связана и с моим профессиональным опытом. Многопоточность уже встречалась мне в одной из рабочих задач, а финансовые рынки являются наиболее близкой мне предметной областью, поскольку я работаю в Т-Инвестициях.

## Сценарий работы приложения

На вход приложение получает CSV-файл со списком тикеров, периодами и интервалами загрузки.

Пример:

```csv
symbol,date_from,date_to,interval
AAPL,2025-01-01,2025-01-10,1d
MSFT,2025-01-01,2025-01-10,1d
NVDA,2025-01-01,2025-01-10,1d
```

После запуска приложение:

1. проверяет корректность входных данных;
2. получает исторические цены через HTTP API;
3. параллельно обрабатывает запросы по разным тикерам;
4. преобразует ответы внешнего сервиса во внутренние модели;
5. передаёт полученные истории в очередь на запись;
6. сохраняет данные каждого тикера в отдельный CSV-файл;
7. нормализует цены к начальному значению 100;
8. строит сравнительный график;
9. формирует итоговый отчёт и журнал событий.

Общая схема работы:

```text
CSV с запросами ->
-> параллельные HTTP-запросы ->
-> ограниченная очередь результатов ->
-> сохранение отдельных CSV-файлов ->
-> нормализация данных и построение графика ->
отчёт о запуске и журнал событий
```

## Параллельная обработка

Запросы по разным тикерам не зависят друг от друга. При последовательной обработке приложение большую часть времени ожидает ответа внешнего сервиса, поэтому для загрузки данных я использовал пул рабочих потоков на основе `ThreadPoolExecutor`.

Количество потоков можно менять через настройки приложения. Это позволяет использовать один и тот же код как для последовательного запуска, так и для параллельной обработки.

Получение данных и их сохранение разделены. После успешной загрузки история цен передаётся через потокобезопасную очередь в отдельный поток записи. Размер очереди ограничен, поэтому результаты не могут накапливаться в памяти бесконтрольно, если сохранение выполняется медленнее загрузки.

Последовательный вариант также оставлен в проекте. Он используется как базовая точка сравнения и позволяет оценить эффект от параллельного выполнения на одном и том же наборе запросов.

## Работа со сбоями

При работе с внешним сервисом возможны сетевые ошибки, тайм-ауты, временная недоступность и ограничение частоты запросов. Поэтому приложение выполняет повторные попытки при:

- сетевых сбоях
- тайм-аутах
- HTTP 408
- HTTP 429
- HTTP 5xx

Между попытками используется увеличивающаяся задержка. Количество попыток и параметры задержки можно задавать через переменные окружения.

Постоянные ошибки не повторяются бесконечно. После исчерпания допустимого количества попыток запрос считается неуспешным, но это не останавливает весь запуск. Истории, которые удалось получить, продолжают обрабатываться и сохраняются на диск.

Такой подход позволяет получить частичный результат даже при проблемах с отдельным тикером.

## Тестовый сервис на Go

Для воспроизводимой проверки ошибок и задержек мне был нужен управляемый внешний сервис. При использовании реального API невозможно заранее определить, когда он вернёт `429`, `503` или будет отвечать медленно.

Поэтому я написал небольшой HTTP-симулятор на Go. Для меня это стало первой практической работой с этим языком. Симулятор использует только стандартную библиотеку и поддерживает несколько заранее определённых сценариев.

| Тикер | Поведение |
|---|---|
| обычный тикер | успешный ответ |
| `SLOW` | успешный ответ с искусственной задержкой |
| `FLAKY` | две ошибки `503`, затем успешный ответ |
| `RATE` | две ошибки `429`, затем успешный ответ |
| `FAIL` | постоянная ошибка `503` |

Симулятор используется как вспомогательный инструмент для интеграционных проверок. Он позволяет многократно воспроизводить одинаковые условия и не зависеть от текущего состояния реального внешнего API.

В одном из проверочных сценариев Python-приложение обработало пять запросов:

- четыре истории были успешно загружены и сохранены;
- один запрос завершился постоянной ошибкой;
- для временных ошибок было выполнено шесть повторных попыток;
- медленный ответ не заблокировал выполнение остальных запросов;
- приложение корректно завершило запуск и сформировало итоговый отчёт.

## Результаты параллельной обработки

Для сравнения последовательного и параллельного вариантов я подготовил десять независимых запросов. Тестовый сервис задерживал каждый ответ на одну секунду.

| Количество рабочих потоков | Время загрузки |
|---:|---:|
| 1 | 10,037 с |
| 5 | 2,013 с |

В этом сценарии переход с одного рабочего потока на пять сократил время загрузки примерно в **4,99 раза**.

Эксперимент проводился на независимых сетевых запросах с одинаковой искусственной задержкой. Поэтому полученный результат не является универсальной оценкой производительности для любых условий. Он показывает эффект параллельной обработки именно в ситуации, когда основное время занимает ожидание внешнего сервиса.

## Автоматический запуск

Приложение решает пакетную задачу: получает список запросов, обрабатывает его, сохраняет данные и завершает работу. Поэтому я не стал искусственно превращать его в постоянно работающий веб-сервис.

Для автоматической проверки и запуска я настроил GitHub Actions. После отправки изменений в репозиторий workflow:

1. создаёт чистое окружение
2. устанавливает Python и Go
3. устанавливает зависимости проекта
4. запускает автоматические тесты
5. выполняет статические проверки Python-кода
6. проверяет Go-симулятор
7. запускает симулятор внешнего поставщика
8. запускает Python-приложение
9. сохраняет созданные CSV-файлы, график, JSON-отчёт и журнал событий как артефакты

Таким образом, полный сценарий проекта воспроизводится независимо от конфигурации моего компьютера. Успешное выполнение workflow подтверждает, что приложение устанавливается, проверяется и запускается в чистом окружении.
