# Market Data платформа


Этот проект я начал с простой задачи: получить исторические цены нескольких биржевых инструментов, сохранить их в удобном формате и построить сравнительный график. По мере разработки мне стало интереснее не только получить данные, но и разобраться, как организовать их параллельную загрузку, обработать сбои внешнего сервиса и сделать результат запуска наблюдаемым.

В итоге получился небольшой сервис пакетной обработки рыночных данных. Он читает список запросов из CSV-файла, обращается к внешнему HTTP API, сохраняет историю каждого тикера отдельно и строит график изменения цен.

Выбор тематики проекта обсуловлен в первую очередь тремя факторами:

1. Проект был предложен для самостоятельной реализации на курсе "Многопоточность в Python: от новичка до эксперта"
2. Проект захватывает тему многопоточности, которая пригодилась мне в одном из рабочих проектов.
3. Работа с финансовыми рынками является для меня наиболее понятной, так как я начал и продолжаю свой путь в Т-Инвестициях 

## Что делает проект

На вход приложение получает CSV-файл со списком тикеров, периодами и интервалами загрузки.

Пример:

```csv
symbol,date_from,date_to,interval
AAPL,2025-01-01,2025-01-10,1d
MSFT,2025-01-01,2025-01-10,1d
NVDA,2025-01-01,2025-01-10,1d
```

Дальше приложение:

1. проверяет входные данные
2. параллельно запрашивает историю цен
3. преобразует ответы внешнего сервиса во внутренние модели
4. сохраняет каждый тикер в отдельный CSV-файл
5. нормализует цены к начальному значению 100
6. строит сравнительный график
7. сохраняет отчёт о выполнении и журнал событий

После запуска результаты находятся в каталогах:

```text
data/prices/
data/charts/
data/reports/
data/logs/
```

## Почему я добавил параллельную загрузку

Запросы разных тикеров не зависят друг от друга. Большую часть времени приложение ожидает ответ внешнего сервиса, поэтому последовательная загрузка использует ресурсы неэффективно.

Для загрузки я использовал пул потоков. Количество рабочих потоков можно менять через настройки. Сохранение результатов выполняется через отдельную ограниченную очередь, чтобы полученные данные не накапливались в памяти без контроля.

Общая схема выглядит так:

```text
CSV с запросами -> параллельные HTTP-запросы -> очередь результатов -> сохранение CSV-файлов -> построение сравнительного графика
```

Я сохранил в проекте и последовательный вариант загрузки. Он нужен как простая точка сравнения и помогает увидеть эффект от параллельной обработки.

## Работа со сбоями

Как это часто встречается на практике, особенно в последнее время, внешний сервис может отвечать медленно, временно быть недоступным или ограничивать частоту запросов. Поэтому приложение повторяет запросы при сетевых сбоях, тайм-аутах, ответах `408`, `429` и `5xx`.

Между попытками используется увеличивающаяся задержка. Эту практику я брал из рабочего опыта. Количество попыток и параметры задержки можно изменить через переменные окружения.

При этом ошибка одного тикера не останавливает весь запуск. Успешно загруженные данные сохраняются, а информация о сбое попадает в итоговый отчёт.

## Наблюдаемость

После каждого запуска приложение формирует два файла:

```text
data/reports/latest.json
data/logs/latest.jsonl
```

В JSON-отчёте сохраняются основные результаты:

- идентификатор запуска
- количество входных запросов
- число загруженных и сохранённых историй
- количество ошибок
- число повторных попыток
- время загрузки
- информация о созданном графике

Журнал событий содержит более подробную последовательность выполнения: начало запуска, успешные загрузки, повторные запросы, ошибки и завершение.

Я добавил эти файлы, чтобы результат работы приложения можно было проверить не только по сообщениям в терминале.

## Тестовый сервис на Go

Для проверки временных ошибок и задержек мне был нужен управляемый внешний сервис. Реальный API не позволяет заранее определить, когда именно он вернёт `429` или `503`, поэтому воспроизводимые проверки с ним неудобны.

Я сделал небольшой симулятор на Go, который поддерживает несколько сценариев:

| Тикер | Результат |
|---|---|
| обычный тикер | успешный ответ |
| `SLOW` | ответ с задержкой |
| `FLAKY` | две ошибки `503`, затем успешный ответ |
| `RATE` | две ошибки `429`, затем успешный ответ |
| `FAIL` | постоянная ошибка `503` |

Go-сервис используется только как вспомогательный тестовый инструмент. Он не является отдельным компонентом проекта. 
Это же стало моей первой практикой в радоте с Golang

Запуск симулятора:

```bash
cd simulator
go run .
```

После этого Python-приложение можно направить на локальный сервис:

```bash
MARKET_DATA_PROVIDER_URL=http://localhost:8080/v8/finance/chart/ \
MARKET_DATA_REQUEST_FILE=config/simulator-requests.csv \
python -m market_data
```

В проверочном сценарии приложение успешно обработало четыре запроса из пяти. Для временных ошибок были выполнены повторные попытки, а постоянная ошибка одного тикера не остановила обработку остальных.

## Результат параллельной обработки

Для сравнения я использовал 10 независимых запросов. Тестовый сервис задерживал каждый ответ на одну секунду.

| Количество потоков | Время загрузки |
|---:|---:|
| 1 | 10.037 с |
| 5 | 2.013 с |

В этом сценарии переход с одного рабочего потока на пять сократил время загрузки примерно в 4.99 раза.

Это не универсальная оценка производительности приложения. Результат получен на специально подготовленном сценарии с независимыми сетевыми запросами и одинаковой искусственной задержкой. Он показывает именно то, что параллельная загрузка позволяет не ожидать завершения каждого запроса последовательно.

## Установка и запуск

Для проекта используется Python 3.13. Выбор версии случайный

```bash
git clone https://github.com/alexsavchenko1/market-data-project.git
cd market-data-project

python3 -m venv .tickerforge
source .tickerforge/bin/activate

pip install -e .
```

Обычный запуск:

```bash
python -m market_data
```

По умолчанию запросы читаются из файла:

```text
config/requests.csv
```

## Настройки

Основные параметры можно изменить через переменные окружения.

Например:

```bash
MARKET_DATA_MAX_WORKERS=2 \
MARKET_DATA_MAX_QUEUE_SIZE=1 \
python -m market_data
```

Доступны настройки адреса поставщика, входного файла, выходных каталогов, количества потоков, размера очереди, тайм-аутов и повторных попыток.

Основные переменные:

```text
MARKET_DATA_PROVIDER_URL
MARKET_DATA_REQUEST_FILE
MARKET_DATA_OUTPUT_DIRECTORY
MARKET_DATA_MAX_WORKERS
MARKET_DATA_MAX_QUEUE_SIZE
MARKET_DATA_MAX_ATTEMPTS
MARKET_DATA_REQUEST_TIMEOUT_SECONDS
MARKET_DATA_CONNECT_TIMEOUT_SECONDS
```

## Ограничения

Проект не является торговой системой и не используется для принятия инвестиционных решений.

Сейчас данные сохраняются локально, а приложение рассчитано на пакетную обработку сравнительно небольшого списка тикеров. В качестве основного источника используется неофициальный HTTP API Yahoo Finance, поэтому его формат или доступность могут измениться.


## Автоматический запуск

Я не стал разворачивать проект как постоянно работающий веб-сервис, потому что приложение решает пакетную задачу: получает список запросов, обрабатывает их и сохраняет результат.

Для автоматического запуска я использовал GitHub Actions. После отправки изменений в репозиторий GitHub:

1. устанавливает Python и Go
2. устанавливает зависимости проекта
3. запускает тесты и статические проверки
4. проверяет Go-симулятор
5. поднимает симулятор внешнего поставщика
6. запускает Python-приложение
7. сохраняет созданные CSV-файлы, график, отчёт и журнал событий

Результаты запуска можно скачать со страницы workflow в виде артефакта `market-data-results`.

Такой вариант позволяет проверить весь сценарий проекта в чистом окружении и не зависит от настроек моего ноута.
